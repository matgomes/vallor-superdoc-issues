# SD-07 — `selection.current().activeChangeIds` reports raw revision ids and omits paragraph-level changes

Part of the deleted-text group: SD-06, SD-07, SD-08, SD-25, SD-40.

## Summary

A live editor selection's `activeChangeIds` is the one portable signal an
integrator has for "which tracked changes does this selection cover," and
it's the natural input to an ids-based accept/reject. Two defects make it
unreliable: it mixes a non-canonical per-revision id in with the canonical
`trackChanges.list()` id for the same logical change, and it omits
paragraph-level changes (a tracked paragraph-mark deletion) entirely — even
though `trackChanges.list()` reports them. For contract review this means a
selection-driven Accept/Reject can leave paragraph-break and
paragraph/run-formatting changes behind with no indication they were missed.

## Environment

- **superdoc 2.23.0 / @superdoc/sdk 2.20.0: REPRODUCES** (both defects).
- Bare `new SuperDoc({ selector, document, user })` mount, Chromium via Playwright 1.64.0; part (c) uses the headless `@superdoc/sdk` `createSuperDocClient({runtime:"v2"})`.

## Steps to reproduce

Two fixtures:

- `whole-paragraph-deleted.docx` — same as SD-06 (P1 kept / P2 tracked-deleted whole paragraph / P3 kept).
- `paragraph-mark-merge-tracked.docx` — generated by `make-fixture.mjs` from `_fixtures/tc-probe-00-clean-backspace-base.docx` via SuperDoc's own tracked `doc.blocks.merge({changeMode:"tracked", ...})` on the paragraph/list-item boundary, producing one `structural` / `paragraph-mark-deletion` tracked change.

UI steps (what a reviewer does), both fixtures:
1. Open the document.
2. Select from inside the first paragraph through a point in the third paragraph (a selection that fully contains the tracked change in the middle).
3. Inspect what the selection reports as "active" tracked changes (e.g. to highlight them in a review sidebar, or to build an ids-based Accept call).

Script: `node SD-07/repro.mjs`. In the browser it sets the selection via `editor.authoring.setSelectionTarget({target})` (SuperDoc's own public selection-setting surface — no Vallor code) and reads `editor.doc.selection.current({includeText:true})`, comparing `activeChangeIds` against `editor.doc.trackChanges.list()`.

## Expected / Actual

**Expected:** `activeChangeIds` lists ids that resolve 1:1 against `trackChanges.list()`'s ids for every tracked change inside the selection, including paragraph-level changes.

**Actual:**

**(a) Raw per-revision ids, only partially canonical** — selecting across `whole-paragraph-deleted.docx`'s single logical deletion:
- `trackChanges.list()` reports **1** change, id `tc|main%3A%2Fword%2Fdocument.xml|del|word-deleted-paragraph-range|625c4c32`.
- `selection.current().activeChangeIds` reports **2** ids: that same id, **plus** `tc|main%3A%2Fword%2Fdocument.xml|del|sd%3Amain%3A%2Fword%2Fdocument.xml%7Cdel%7CJane%20Doe%7C2026-10-05T12%3A00%3A00Z%7C100%7CwId%3A100` — a raw per-revision ("wId:100") id that `trackChanges.list()` never surfaces on its own. A caller that treats `activeChangeIds` as "one id per logical change" will overcount, and a caller that tries to cross-reference every active id against `list()`'s ids will find one that doesn't resolve.

**(b) Paragraph-level changes omitted entirely** — selecting across `paragraph-mark-merge-tracked.docx`'s `structural`/`paragraph-mark-deletion` change (selection fully contains it, confirmed via the selection's own 3-block `target.segments`):
- `trackChanges.list()` reports **1** change (`type:"structural", subtype:"paragraph-mark-deletion"`).
- `selection.current().activeChangeIds` is **`[]`** — empty. The change is invisible to anything built on `activeChangeIds`.
- Headless sanity: `decide({kind:"ids", ids:[]})` (what a caller gets by forwarding the empty `activeChangeIds`) is refused — `INVALID_TARGET`, `track-changes decide:target.id is required.` `decide({kind:"id", id})` using the real `trackChanges.list()` id succeeds and removes the change, confirming the change itself is perfectly decidable — it's specifically unreachable through the selection's `activeChangeIds`.
- 0 `onException`/console errors in either browser pass.

Full raw output: `results-2.23.0.json`. Screenshots: `screenshots/raw-id-split.png`, `screenshots/paragraph-level-change-omitted.png`.

## Root cause / analysis

`activeChangeIds` appears to be built by walking the live marks under the
selection and emitting one id per raw revision mark (`w:ins`/`w:del`
instance), rather than resolving each mark up to the grouped "logical"
change `trackChanges.list()` canonicalizes marks into. For a simple
run-level deletion this mostly collapses to the canonical id plus one
leftover raw-revision alias (part a). For a paragraph-mark deletion — which
carries no `w:del` run mark at all, only the paragraph-mark-level revision
metadata `trackChanges.list()` classifies as `structural` /
`paragraph-mark-deletion` — the mark-walking approach appears to produce
nothing, hence the empty array (part b). This matches SD-06's own finding on
the same `whole-paragraph-deleted.docx` fixture (used there for a different
assertion), confirming the raw-id behavior is consistent and reproducible,
not fixture-specific.

## Suggested fix

Resolve each mark under the selection to its logical change id (the same
canonicalization `trackChanges.list()` already performs) before populating
`activeChangeIds`, and extend that resolution to paragraph/structural-level
tracked changes (paragraph-mark deletions, paragraph/run formatting
changes), not only run-level insertion/deletion marks. Possible workaround
for integrators until fixed: don't rely on `activeChangeIds` alone for
selection-driven accept/reject — cross-reference the selection's block ids
against `trackChanges.list()`'s `navigationTarget.blockId` to catch
paragraph-level changes the selection covers, and de-duplicate
`activeChangeIds` against `trackChanges.list()`'s canonical ids.
