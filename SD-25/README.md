# SD-25 — Mutation-plan locators can never see tracked-deleted text, so a hidden edit can make a target ambiguous

Part of the deleted-text group: SD-06, SD-07, SD-08, SD-25, SD-40.

## Summary

`find()` and selector-based `mutations.apply` steps have a documented
`includeDeletedText` flag meant to let a locator match text inside a
tracked deletion. In practice this flag never surfaces anything — deleted
text is unconditionally invisible to every selector. The practical
consequence: when a hidden tracked edit is the *only* thing distinguishing
two otherwise-identical visible paragraphs, no selector can ever
disambiguate them, and a multi-step edit plan targeting "the" occurrence
fails. For contract redlining this means an automated or agent-driven edit
plan can refuse to apply near previously-redlined text for no reason visible
to the end user.

## Environment

- **superdoc 2.23.0 / @superdoc/sdk 2.20.0: REPRODUCES.**
- Headless `@superdoc/sdk` `createSuperDocClient({runtime:"v2"})` — pure Document API, no browser needed.

## Steps to reproduce

Fixtures:
- `_fixtures/tc-probe-sd06-fixture.docx` (shared corpus; same doc used in SD-06/07) — one paragraph is entirely a tracked deletion containing the words "whole paragraph."
- `ambiguous-visible-text.docx`, generated by `make-fixture.mjs` from `_fixtures/tc-probe-00-clean-backspace-base.docx`: paragraph 1 is plain text "Widget A costs 150 dollars." (never edited); paragraph 4 started as "Widget A costs 100 dollars." and had "100" tracked-replaced with "150" (`doc.replace({...}, {changeMode:"tracked"})`) — so paragraph 4's **visible** text is now identical to paragraph 1's, but it carries a hidden tracked deletion of "100" that paragraph 1 does not have.

UI steps (what an integrator/agent does):
1. Open a document containing a previously-redlined clause whose visible text now reads the same as another, untouched clause elsewhere in the document.
2. Ask an edit tool (agent action, template fill, find/replace) to change "the" occurrence of that text.
3. Observe: the edit is refused as ambiguous, with no way to say "the one that was previously redlined" — because the redline itself is invisible to the locator.

Script: `node SD-25/repro.mjs`.

## Expected / Actual

**Expected:** `includeDeletedText: true` (per its own doc comment: "includes text from pending tracked deletions in search results") lets a selector see and use deleted text, including for disambiguation; a plan step can either disambiguate using tracked-change context or fail with a specific, actionable conflict code.

**Actual:**
- `doc.find({type:"text", pattern:"whole paragraph"})` on the simple deletion fixture: `total: 0` with `includeDeletedText` **omitted** (expected — default is visible-only).
- The same call with **`includeDeletedText: true`**: `total: 0` — **identical to the default**, i.e. the flag changes nothing.
- `doc.find({type:"text", pattern:"100", includeDeletedText:true})` on the tracked-replacement fixture (where "100" is the literal deleted text of a real tracked change, confirmed via `trackChanges.list()`): `total: 0` — again, the flag surfaces nothing.
- `doc.find({type:"text", pattern:"Widget A costs 150 dollars."})` (plain, no flag): `total: 2` — matches both paragraph 1 (plain) and paragraph 4 (post-tracked-replacement), because their visible text is now identical.
- `doc.mutations.apply({steps:[{op:"text.rewrite", where:{by:"select", select:{...}, require:"exactlyOne"}, ...}]})` on that same ambiguous pattern: refused — `code: "COMMAND_FAILED"`, `message: "selector matched 2 ranges, expected exactly one."` There is no way to pass additional context (e.g. "the one near a tracked change") to resolve the ambiguity, because the disambiguating content is categorically unreachable by any selector.

Full raw output: `results-2.23.0.json`.

## Root cause / analysis

The visible-text projection selectors run against appears to exclude
tracked-deletion content unconditionally — `includeDeletedText` is wired as
an input field on `TextSelector` but, empirically, has no effect on the
result set on this version. Any locator-based operation (`find`, `query.match`,
and `mutations.apply` steps using `by:"select"`) therefore cannot distinguish
two spans of visible text when the only difference between them is tracked
history. This matches the broader "locators can't match across/near hidden
deleted text" pattern: a `within` scope, a lookaround-style regex, or a
disambiguating neighbor that happens to be inside a tracked deletion are all
equally unreachable, because the deleted content never enters the candidate
text at all, flag or no flag.

## Suggested fix

Honor `includeDeletedText: true` in the text-matching projection used by
`find`/selectors (and by extension, `mutations.apply` `by:"select"` steps) —
include tracked-deletion runs as literal, matchable text (not necessarily
rendered) when the flag is set, exactly as documented. Once this works,
expose a way for a selector/step to require or forbid a specific tracked-
change id or author as disambiguating context, so the ambiguity in the
scenario above can be resolved programmatically. Possible workaround for
integrators until fixed: pre-filter candidate blocks by `navigationTarget`
from `trackChanges.list()` before constructing a text selector, and target
by block id (`by:"block"`) instead of a free-text pattern whenever a
document may contain tracked edits near the target text.

## Notes / caveats

- `AMBIGUOUS_MATCH`, `TARGET_CONFLICT`, and `PLAN_CONFLICT_OVERLAP` (the
  specific error-code names referenced in earlier internal notes) were not
  observed verbatim in this pass — the actual refusal code on 2.23.0 for an
  over-matched `require:"exactlyOne"` selector is `COMMAND_FAILED` with the
  message quoted above. Multi-step plans with genuinely overlapping target
  ranges, and a regex lookaround pattern reaching across a paragraph
  boundary into a deletion, were not separately retested — time-boxed out;
  the `includeDeletedText` finding above is the root cause common to all of
  these framings, so further variants would likely surface the same
  underlying gap rather than a materially different one.
